# Implementation Plan: Extensible Game Item System & Strategy Pattern

**Branch**: `010-game-item-system` | **Date**: 2026-10-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/010-game-item-system/spec.md`

## Summary

Generalize game item handling in the DUT-AI Quiz arena backend from an imperative `if-elif-else` ladder in `UseItemGameUseCase` to an extensible **Strategy Pattern** backed by a centralized **Game Item Registry**:
1. **Item Strategy Abstraction**: Define `IGameItemStrategy` and value objects (`ItemExecutionContext`, `ItemExecutionResult`) encapsulating item validation, pricing calculation, and state mutations.
2. **Dedicated Concrete Strategies**:
   - `MicroscopeItemStrategy`: Encapsulates question option retrieval, incorrect option filtering, random sampling, and gold deduction.
   - `TimeFreezeItemStrategy`: Encapsulates freeze timer flag activation and pricing.
   - `TurnBuffItemStrategy` (`DoublePointsItemStrategy`, `ShieldItemStrategy`): Rejects instant activation attempts with domain validation exceptions, clarifying turn-based lifecycle rules.
3. **Item Registry (`GameItemRegistry`)**: Central lookup service mapping `GamificationItem` to its registered strategy instance, wired via Dishka dependency injection.
4. **Refactored Use Case Coordinator**: Transform `UseItemGameUseCase` into a lightweight, decoupled orchestrator with 0 conditional branches checking item types.
5. **Zero Breaking Changes**: Preserve 100% backward compatibility for API schemas (`GamificationUseItemIn` and `GamificationUseItemResultOut`).

## Technical Context

**Language/Version**: Python 3.12 (Backend)  
**Primary Dependencies**: FastAPI, Pydantic v2, Dishka (DI), SQLAlchemy 2.0 / SQLModel  
**Storage**: PostgreSQL (`game_sessions`, `game_questions`)  
**Testing**: Pytest (`pytest-asyncio`), `uv run pytest apps/api/test/`  
**Target Platform**: Linux / macOS server (Docker containerized)  
**Project Type**: Monorepo Web Application (`apps/api`)  
**Performance Goals**: Item activation endpoint response time < 25ms; zero regression overhead  
**Constraints**: Zero hardcoded item `if-elif-else` ladders in use cases; atomic state mutation & resource deduction; 100% type safety and clean DDD layer separation  
**Scale/Scope**: Refactoring 1 use case, creating 1 interface, 2 value objects, 1 registry, 3 concrete strategies, and updating DI bindings + unit tests

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- [x] **Principle I (Lightweight DDD)**: Concerns remain strictly separated. The domain interface `IGameItemStrategy` and value objects (`ItemExecutionContext`, `ItemExecutionResult`) reside in `app/domain/interfaces/` and `app/domain/value_objects/`. Concrete strategies implementing repository calls and the `GameItemRegistry` reside in `app/application/services/game_items/`. `UseItemGameUseCase` remains a clean application coordinator.
- [x] **Principle II (Single Source of Truth API Contracts)**: Existing API response models (`GamificationUseItemResultOut`) and input models (`GamificationUseItemIn`) are preserved without any contract breaking changes or payload drift.
- [x] **Principle III (Feature-First Frontend)**: Frontend contract remains untouched. No frontend changes are required because the API response and error contracts remain identical.
- [x] **Principle IV (Test-Driven Verification)**: 100% test pass rate across `apps/api/test/` (including all 149 existing tests and new dedicated unit tests for strategies and the registry).
- [x] **Principle V (Authority & State Separation)**: The server retains sole authority over gold deduction, option elimination calculations, and game state mutations.
